# Tessera — V1

Fetch videos from a list of YouTube channels, pull their transcripts, store in SQLite.
Runs locally on macOS. No API key, no OAuth, no quota. Nothing leaves the machine.

## Scope of this document

This is the design-for-build record, kept in writing order: V1 (the corpus),
V1.1 (the read-only browser UI), the grounded ASR normalization experiment, and
V2 (fetch also normalises and summarises). Where implementation proved the design
wrong, the correction is written into the original section rather than papered
over. The channel list ships as `channels.json.example` and the working list
stays untracked; phases after V2 — video chat, timestamped passages, read
markers, the local Whisper fallback, the scheduled theme — are documented in
`README.md` and in the commit history, one commit per change.

## Goal

Build a local corpus of videos + transcripts. V1 produces NO summaries and NO
recommendations. It is the data layer that V2 (rank + summarize with a local LLM)
will sit on top of.

## Location

New project directory: `~/sources/tessera` (does not exist yet — created on build).

Separate from `~/sources/youtube`, which stays empty.

## Setup

```bash
mkdir -p ~/sources/tessera && cd ~/sources/tessera
uv venv --python 3.14      # reuses brew's 3.14.7, no interpreter download
uv sync                    # creates .venv, installs deps, writes uv.lock
```

`uv venv --python 3.14` finds the Homebrew interpreter already on the machine and
symlinks it, rather than downloading its own managed CPython. Nothing to
`brew install` first.

Use `uv run` rather than `source .venv/bin/activate` — it resolves the environment
from `.venv` automatically, so there's no shell state to get wrong.

### Python 3.14 compatibility — verify at build time

3.14 is new enough that wheel coverage for some C extensions is still incomplete.
The risk is `youtube-transcript-api` → `browser-cookie3`, which pulls in a
cryptography dependency that may have no cp314 wheel and would then build from
source.

`uv sync` will surface this immediately as a build failure. If it happens, the fix
is one command — 3.13 has near-universal wheel coverage:

```bash
uv venv --python 3.13 --clear && uv sync
```

Nothing in this project needs 3.14 specifically. Pure-Python 3.13 is the safe
default if the build complains.

### Dependencies

Deliberately few:

| package | why |
|---|---|
| `youtube-transcript-api` | fetches caption tracks |

SQLite, RSS/XML parsing, and argparse are all stdlib. (`requests` arrives
transitively via `youtube-transcript-api`; nothing imports it directly.)

> **Revised during implementation.** This plan originally also depended on
> `browser-cookie3`, reading Firefox `cookies.sqlite` so requests would "look like
> a normal logged-in browser." That is not possible with the current library — see
> "Cookies do not work" under Known limits. The dependency, the module, and the
> associated design risk were all removed.

Declared in `pyproject.toml` rather than `requirements.txt` so `uv sync` produces
a `uv.lock` with exact pinned versions — `uv sync` then recreates the environment
byte-identically on any machine, months from now. For a ~200-line script this is
arguably more than needed, but V2 adds an LLM client and this is where that
belongs.

## Channels

`channels.json` — a plain list of YouTube channel IDs. Edit it by hand.

```json
[
  { "id": "UCBa659QWEk1AI4Tg--mrJ2A", "name": "Computerphile" },
  { "id": "UCoUxsWakJucWg46KW5RsvPw", "name": "Financial Times" }
]
```

`name` is cosmetic, for display in `status`.

Two example channels, deliberately different in production cadence so the ingest
logic gets exercised properly:

| channel | topic | language | cadence |
|---|---|---|---|
| Computerphile | computer science explainers | English | ~1/week |
| Financial Times | journalism, originals | English | ~5/week |

Both are English-language, which is fine for V1 — the native-track rule is
language-agnostic, but a French channel is a useful third data point later.

## How it works

1. For each channel, GET `https://www.youtube.com/feeds/videos.xml?channel_id=<id>`
   - Public RSS. No key, no auth, not rate limited.
   - Returns the 15 most recent uploads with video ID, title, description,
     publish date, channel name.
2. Keep entries published within the last `WINDOW_DAYS` (see config).
3. For each kept video, try to fetch its transcript.
4. Store both in SQLite.

Transcripts come from `youtube-transcript-api`, which reads the caption track
that YouTube already serves to the player. Pass Firefox cookies so requests look
like a normal logged-in browser — this is what keeps YouTube from blocking us.

## Transcript language

Take the video's native caption track. That's it — no language list, no
fr/en preference, no translation. If a channel publishes in French you get
French, if English you get English. `youtube-transcript-api` already returns the
native track first; we just take the first result that isn't an auto-translation.

Preference between caption types, when several exist:
- manual captions first (author-written, higher quality)
- auto-generated captions otherwise
- never an auto-translated track

## What `fetch` does

`fetch` runs two selection paths, then works through whatever they return.

**Path 1 — ingest.** Fetch each channel's RSS, keep entries within `WINDOW_DAYS`,
insert any video not already in `videos`.

**Path 2 — retry.** Select transcripts where `status` is `blocked` or `error` and
`attempts < MAX_ATTEMPTS` (3). **This ignores publish date on purpose.**

That second part matters more than it looks. A video published 9 days ago that
came back `blocked` would never be selected again under a date filter, so it
becomes permanently unreachable — recovering it would require widening
`WINDOW_DAYS`. Driving retries off the transcripts table rather than the date is
what prevents that.

Both paths mean `fetch` is idempotent (running twice leaves the same state) *and*
self-healing (transient failures clear on the next ordinary run). There is no
separate retry command to remember. After `MAX_ATTEMPTS` a row stops retrying and
shows up in `status` as needing attention — the honest outcome for something
genuinely broken rather than unlucky.

Videos already stored and transcripts already `ok` are skipped, so daily runs are
near-free after the first.

## Schema

```sql
CREATE TABLE videos (
  video_id      TEXT PRIMARY KEY,
  channel_id    TEXT NOT NULL,
  channel_name  TEXT,
  title         TEXT NOT NULL,
  description   TEXT,
  published_at  TEXT NOT NULL,   -- ISO8601 UTC, from the RSS feed
  url           TEXT NOT NULL,
  first_seen_at TEXT NOT NULL
);

CREATE TABLE transcripts (
  video_id    TEXT PRIMARY KEY REFERENCES videos(video_id),
  lang        TEXT,             -- native language code, e.g. 'en' / 'fr'
  kind        TEXT,             -- 'manual' | 'auto'
  status      TEXT NOT NULL,    -- see below
  text        TEXT,
  attempts    INTEGER DEFAULT 0,
  error       TEXT,
  fetched_at  TEXT NOT NULL
);

CREATE INDEX idx_videos_published ON videos(published_at DESC);
CREATE INDEX idx_videos_channel   ON videos(channel_id);
CREATE INDEX idx_transcripts_status ON transcripts(status, attempts);
```

`chars INTEGER` sat in that table through V1.1's first build and has since been
dropped. See "Left pane" for why a stored character count was the wrong shape for
the only question it was being used to answer.

One transcript per video (native only) — no need for a composite key.
`channels.json` is the source of truth for the channel list; it's not duplicated
into the database.

The `transcripts(status, attempts)` index exists purely to make path 2 cheap.

### `status` values

| value | meaning | retried? |
|---|---|---|
| `ok` | transcript stored | — |
| `no_captions` | video genuinely has no captions | no, permanent |
| `disabled` | captions exist but the author turned them off | no, permanent |
| `unavailable` | private, removed, or age/region blocked | no, permanent |
| `blocked` | YouTube rate-limited or challenged us | **yes** |
| `error` | anything else, including a bug in our cleanup code | **yes** |

The split between the last two and the first three is load-bearing, not
documentation — it is literally the WHERE clause for path 2. Without it a retry
pass re-hammers permanently-captionless videos forever.

## Caption cleanup

Auto-generated captions are noisy. Raw output contains:

- Rolling duplicated lines — `the cat` / `and the cat` / `cat sits on` / `the mat`,
  where each line repeats the tail of the previous one
- Inline noise tags — `[Music]`, `[Applause]`, `[laughter]`, `[silence]`, `[inaudible]`

Clean both before storing. Without this the text reads as broken half-sentences and
any summary built on it will be poor. Manual captions are usually clean already but
get the same pass for safety.

This matters more for noisier uploads than for clean studio audio: videos with
music, kitchen or ambient noise are almost always auto-captioned, with heavy
background noise, `[Music]` overlays, and overlapping speech. Expect
`kind = 'auto'` on nearly every row of a channel publishing that kind of video.

Cleanup is pure string processing, no model, no dependencies.

## Window size

No CLI flag. `WINDOW_DAYS = 7` lives in `config.py`.

Running `fetch` daily with a sliding window catches everything regardless of how
often a channel publishes — caching means already-seen videos cost nothing.

**To seed a backlog:** temporarily set `WINDOW_DAYS = 90` in `config.py`, run
`fetch`, set it back to 7. That's the whole mechanism.

## First run

```bash
uv sync
# set WINDOW_DAYS = 90 in config.py
uv run tessera fetch
# set it back to 7
uv run tessera status
```

Expect the ~15 newest videos per channel, though with a fast channel the RSS cap
means the count is incomplete — see below.

## Deliverable / how to tell it worked

`tessera status` reports per channel: videos found, transcripts `ok`, and a
breakdown of failures with video IDs and reasons.

That failure breakdown is the real output of V1. It's the measurement of whether
the cookie approach is holding up against YouTube, which is the main risk in this
whole design. If `blocked` dominates, we revisit cookie handling before building
anything on top.

## Known limits

- **RSS returns 15 entries max, and this now bites.** For a weekly channel a
  15-entry feed covers 15 weeks — never a problem. For one posting ~3/week, 15
  entries cover only **33 days**, so a 90-day backfill returns 15 videos instead
  of the ~41 that exist in that window. About 26 older videos are silently
  missed.
  Steady-state daily runs are unaffected, since only new arrivals matter and those
  are always within 15. The fix, if the missed backlog matters, is paginating via
  yt-dlp's flat playlist listing, or accepting the gap for now. Out of scope for V1.
- **A fixed window never reconsiders old videos.** Anything outside it is never
  fetched. Fine while the goal is "recent uploads" — V2's backlog has to come from
  a temporary wider `WINDOW_DAYS`.
- **Cookies do not work, and the plan's central premise was wrong.** The plan
  assumed Firefox cookies would make requests look like a logged-in browser and
  therefore "keep YouTube from blocking us." As of `youtube-transcript-api`
  **v1.1.0** (2025-06-11) the library fetches captions from YouTube's *innertube*
  API rather than scraping the `/watch` page, and the maintainer disabled cookie
  authentication explicitly:

  > Unfortunately, I haven't been able to implement authentication for the
  > innertube API yet. As I wanted to provide a fix for this issue ASAP, I
  > decided to disable cookie authentication for the time being.

  Still disabled in v1.2.4, seven months later. Two consequences:

  1. The innertube call authenticates via an `Authorization` header. The library
     sets no `Authorization`, no `SAPISIDHASH`, and no visitor data — it
     impersonates an anonymous `ANDROID` client. Browser cookies cannot
     substitute for that, so they can only influence the intermediate watch-page
     fetch, never the call that returns captions.
  2. Even where they did help, the library's own error text warns that
     authenticating with cookies gets **the account permanently banned**. The
     maintainer does not recommend it.

  So `cookies.py` and the `browser-cookie3` dependency are gone, and `blocked`
  rows are no longer treated as a cookie problem. If `blocked` dominates in
  normal use, the remaining levers are `POLITE_DELAY` and a proxy via
  `ProxyConfig` — neither of which is free.
- **Each transcript costs one full watch-page download**, not a light API call,
  since innertube keys are scraped from the page HTML first. This is why
  `POLITE_DELAY` is 5s.

## Explicitly out of scope for V1

- Summaries or any LLM involvement
- Ranking, scoring, or recommendations
- Scheduled/daily runs (`launchd`)
- Tracking which videos you've watched

# Tessera — V1.1: browser UI

A read-only browser view of the corpus. Three panes: video list, YouTube player,
transcript.

This is a new phase, not a revision of V1. The V1 spec above stands as written —
including "Explicitly out of scope for V1", which lists summaries, search, and
watched-video tracking. This phase adds none of those.

## Decisions

| question | answer |
|---|---|
| transcript synced to playback? | **no** — no `cues` table, no schema change, no refetch |
| serving | stdlib `ThreadingHTTPServer`, no new dependency |
| write access | **`GET` only**, enforced at the SQLite engine |
| front end | **Web Components** — custom elements, Shadow DOM, `<template>` |
| layout | three columns — channel list, player, transcript |
| pagination | server-side `limit`/`offset`, default 200, clamped at 500 |
| video list ordering | flat `published_at DESC`, **not** grouped by channel |

### Why there is no transcript↔playhead sync

This was the first design question and it was decided against. The obvious
version of this feature — click a line, seek the video — is **not implementable
against the current schema**, because `transcript.py` discards timing:

```python
text = clean_captions("\n".join(snippet.text for snippet in fetched))
```

`FetchedTranscriptSnippet` carries `start` and `duration`, so the data exists at
fetch time and is thrown away. Supporting sync means a `cues` table, per-cue
cleanup (today's `clean_captions` is whole-blob only, which is what blocked it),
and a refetch campaign for the 14 transcripts already stored.

That is a real cost, so it was weighed rather than assumed. What sync would buy:
click-to-seek, auto-scroll, and a highlighted current line. What is given up in
exchange, with no sync: **nothing about playback.** The nocookie embed is already
a complete player — its own scrub bar, duration readout, speed control,
fullscreen. Only the coupling between transcript and playhead is lost.

So the honest framing is: this is a *read-along* tool, not a transcript player.
Reopening this means accepting the schema change and the refetch; it is not a
frontend problem.

### Why Web Components

The brief is explicit: custom elements + Shadow DOM + `<template>`. The reasons
that hold up here, so the choice is not just restated:

- **Shadow DOM** makes the page's CSS scope moot. `app.js` can use whatever
  class names it likes, and none of them can reach into a component or collide
  with anything else. No naming convention, no prefix discipline.
- **`<template>`** content is inert. Custom elements nested inside it do not
  upgrade and no `<img>` inside it loads until it is cloned into a shadow root.
  That is the whole point of using it over an `innerHTML` string.
- **Custom elements** give each pane a real lifecycle and a real API, so the
  list, the player, and the transcript can be developed and reasoned about
  separately without a framework's reconciliation model anywhere in sight.

Cost accepted: four elements, a hand-written state contract, and no build step.
In exchange, no `node_modules`, no bundler, no framework version to pin.

## Component contract

State travels **down as properties**, events travel **up as `CustomEvent`s**.
Attributes are used only for values that are genuinely single strings and worth
reflecting (`selected`).

| element | properties in | event out |
|---|---|---|
| `<tessera-app>` | — (owns `channel`, `status`, `offset`) | — |
| `<tessera-video-list>` | `rows`, `meta`, `filter`, `selected`, `notice` | `select`, `filter-change` |
| `<tessera-video-player>` | `detail` | — |
| `<tessera-transcript>` | `detail` | — |

`detail` is the whole `/api/videos/<id>` row, or `null`. It began as four
separate properties (`videoId`, `text`, `status`, `error`) and was collapsed to
one: four properties set in sequence let a render land on a half-updated
transcript — new `videoId`, old `text` — and the pane would show one video's
text under another's title. One object is one assignment and cannot tear.

`filter` is `{channel, status, offset}` — the query the list is displaying. The
list is a controlled component and needs the offset to render the pager and to
build the next request. It is not where the state lives; `<tessera-app>` is.

`notice` covers the two states where there is no page to show: `Loading…`, and
the message from a failed request. One property rather than `loading` plus
`error`, because they occupy the same slot in the layout.

`filter-change` carries the **complete desired query**, not a patch. One rule for
what a filter change means, instead of a merge rule in one component and an
offset reset in another. The list sends `offset: 0` whenever it changes `channel`.

The collection goes in as a **property, not an attribute**. Attributes are
strings; an array of video objects would have to be serialised into one, which is
both wrong and a second copy of the data. Assign `list.rows = rows` and read it
back off the property.

The channel filter and the page offset are **owned by `<tessera-app>`**, which
refetches when either changes.

This reverses an earlier draft that put the filters inside
`<tessera-video-list>` as local state, on the reasoning that nothing else
consumed them. That reasoning only holds without pagination: the list holds
exactly one page, so it cannot filter what it does not have. With paging, the
controls have to live where the query is built, or the list would be filtering a
page and calling the result a channel.

`<tessera-video-list>` is therefore purely presentational — render `rows`, emit
intent. `<tessera-app>` is the only thing that talks to the network. Components
receive data and emit intent; they never fetch. That keeps every request in one
file and makes the read-only boundary a property of the design rather than a rule
people have to remember.

### Where the `<template>`s live

Each component declares its own template as a string in its own module, cloned in
the constructor. Not `<template>` tags in `index.html` referenced by id.

The id-based version splits a component's markup and behaviour across two files
and creates a load-order dependency — the template must exist before the module
that clones it runs. Self-contained modules have neither problem. The tradeoff is
that the markup loses editor HTML tooling; that is the price of no build step,
and it is paid per-component rather than once.

## Endpoints

Two. Both `GET`.

| route | returns |
|---|---|
| `GET /api/videos?channel=&status=&limit=&offset=` | `{rows, meta}` |
| `GET /api/videos/<id>` | one row including `text` and `description` |

All four parameters are optional, and the **endpoint's** default — a bare
`GET /api/videos` — is every channel, newest first, unpaged. That stays: an
endpoint with a hidden opinionated default is worse than one that answers the
question it was asked.

**`tessera ui` sends `GET /api/videos?status=ok` on load.** The endpoint's own
default stays bare — an endpoint with a hidden opinionated default is worse than
one that answers the question it was asked — but the sidebar asks for transcripts
only. A row it cannot open is not a row; see "Left pane".

The `ok` literal is written down, not fetched. An earlier build published it as
`meta.ok`, on the principle that the client hardcodes no part of the taxonomy.
That principle is right for `total`, `has_more` and `channels`: each is derivable
only from the whole corpus, which a client holding one page does not have. `ok` is
not one of those. It is a literal, and publishing it cost a request per page load
to learn a constant — the first load issued **two** `/api/videos` calls, the first
purely to read a string and the second to apply it.

An intermediate build made it worse and more instructive: the client set
`status = meta.ok` *without* re-requesting, and the list displayed all 23 rows
while claiming `?status=ok`, with a `meta.total` that agreed with neither. The bug
was not really about the second request; it was that the filter had been made
cosmetic. The lesson outlasted the code: the badge was removed and the client
spent a while sending no status at all, but whenever it does filter, the
**server** applies it, so `meta.total` and the pager count exactly what is shown.

`status.js` — one string with three importers — was deleted rather than trimmed.
`transcript.js` writes `OK = 'ok'` locally, and `app.js` carries the second copy
its request needs; a module for a single string is not worth its own file.

`meta` publishes no status values, and the general rule survives intact:
**publish what the client cannot derive; write down what it can.**

Plus the static files: `GET /`, `GET /app.js`, `GET /styles.js`, and
`GET /components/<name>.js` for exact known names only — no path is ever
concatenated into a filesystem path.

**The list endpoint returns neither `text` nor `description`.** `text` is 522,508
characters across 14 rows today, averaging 37k and peaking at 134,632 on
`eCt3AAx0htM`; `description` is the RSS entry's own blurb and runs 1–4KB a
video. A list is metadata. What it does carry is `video_id`, `channel_id`,
`channel_name`, `title`, `published_at`, `url`, `lang`, `kind`, `status`,
`attempts` — `store.py`'s existing status query already selected all of these,
so this query is close to already written. (`chars` was on that list too, and is
not any more; see "Left pane".)

### Filtering and pagination

```
GET /api/videos?channel=&status=&limit=&offset=
 → { rows, meta: { total, limit, offset, has_more, channels } }
```

`meta` is exactly those five keys, and that is asserted as a set rather than
key-by-key, so a key nobody reads cannot be added back by accident.
`max_attempts`, `retryable` and `permanent` were published for all of V1.1 and
read by nobody: the argument for them was that a browser hardcoding its own
taxonomy could quietly disagree with the retry path about what gets another
attempt. But the retry path is `tessera status`, a different process, which reads
`transcript.py` directly — no browser was ever in that loop, so the disagreement
the comment described could not occur. `check_ui.py` asserts both halves now: the
exact key set, and that each published key is genuinely read somewhere in the
client.

- **on load** — `?status=ok`: transcripts only. The sidebar shows what it can
  open; see "Left pane"
- **channel picked** — `?channel=<id>` alongside it, with `offset` reset to 0
- **channel cleared** — `channel` dropped, which is how you get back to every
  transcript; there is no "all channels" button, an empty box is the affordance
- **paging** — `?offset=200`; `limit` defaults to 200 and is clamped at 500

`status=ok` is the only status the UI sends. The endpoint accepts any value and
`check_ui.py` exercises the rest of the taxonomy through it, but a row that
cannot be opened is not in the list, so the other values serve the command line
and the future failures pane rather than the browser.

`limit` is clamped rather than rejected, so a client cannot ask for the whole
table by accident. A non-numeric or negative `limit`/`offset` is a 400 rather
than a silently-ignored value.

`meta.total` counts the **filtered** set, not the table — otherwise "showing
21–40 of 63" is a lie the moment a channel is selected. `meta.has_more` is
`offset + len(rows) < total`, computed server-side so the client never has to
guess whether a short page is the last one or a bad `limit`.

Changing a filter resets `offset` to 0. Without that, selecting a channel while
on page 3 lands on an empty page of a set that has one.

The list is a flat `published_at DESC`, which `idx_videos_published` already
serves directly. The one query that rides no index is the `COUNT(*)` behind
`meta.total`; irrelevant at this size, worth knowing if the corpus grows.

### Why the list is not grouped by channel

An earlier draft grouped rows under channel headers — a reasonable presentation,
dropped for a concrete reason: **grouping and pagination are incompatible.**
Grouping needs the whole set in hand to group it, and page 1 of a
`published_at DESC` query is an interleave of both channels. Making grouping work
per page would mean `ORDER BY channel_name, published_at DESC`, which redefines
"newest" as newest-within-channel and puts page boundaries in the middle of a
group.

A flat feed answers "what is new", which is what a feed is for. The sidebar
channel filter answers "what has this channel got" — without the client needing
every row to do it.

### Why there is no `/api/status`

Dropped on purpose. Every row already carries `status` and `attempts`, so the
"past `MAX_ATTEMPTS`, no longer retried" marker is derivable client-side. A third
endpoint would have been a second query shape computing numbers
`store.status_report` already computes for the terminal command.

`meta.total` covers what a summary endpoint would otherwise have supplied: it is
the one aggregate the client cannot derive, because the client only ever holds
one page.

`meta` exists so the client hardcodes nothing it cannot already know. On load the
sidebar sees:

```json
{"total": 14, "limit": 200, "offset": 0, "has_more": false,
 "channels": [{"id": "UCBa659QWEk1AI4Tg--mrJ2A", "name": "Computerphile"},
              {"id": "UCoUxsWakJucWg46KW5RsvPw", "name": "Financial Times"}]}
```

That is the whole of it. `total` and `channels` are here because **the client
cannot derive them from one page**: past 200 rows a channel whose videos all fell
off the back of the first page would vanish from the picker while still existing in the
corpus, and `total` is the one aggregate a paged client has no way to compute.
`limit`, `offset` and `has_more` are there so the client never has to guess
whether a short page is the last one or a bad `limit`.

`ok`, `max_attempts`, `retryable` and `permanent` were all published here and all
removed. `ok` because publishing it cost a request per page load to learn a
literal — see "Filtering and pagination". The other three because nothing read
them; see below.

The "past `MAX_ATTEMPTS`, no longer retried" marker was then

```js
meta.retryable.includes(row.status) && row.attempts >= meta.max_attempts
```

This mattered more than it looked, and then it turned out not to. The
permanent/retryable split is described throughout this project as "literally the
WHERE clause for path 2", and the UI used to compute its "past `MAX_ATTEMPTS`, no
longer retried" badge from `meta.retryable` and `meta.max_attempts`, on the theory
that a browser hardcoding `['blocked', 'error']` could quietly disagree with
`select_retryable` about what gets retried.

There was no browser in that loop. The retry path is `tessera status`, a
different process, reading `transcript.py` directly — `PERMANENT_STATUSES` and
`RETRYABLE_STATUSES` are imported from the same module the SQL is built in. A
browser disagreeing with them was never a possible failure, so the two keys were
bytes on every list response guarding against nothing.

One source of truth is still the right instinct; it just was never the envelope's
job to provide it.

## Read-only enforcement

```python
sqlite3.connect(f"file:{config.DB_PATH}?mode=ro", uri=True)
```

Verified against the live corpus: `PRAGMA journal_mode = WAL` is a no-op on a
read-only connection (the mode is persistent in the file header, and WAL is
already set), and `UPDATE` raises `attempt to write a readonly database`.

So read-only is enforced by the engine, not by convention — a bug in a handler
cannot mutate the corpus. Alongside it:

- bind `127.0.0.1` explicitly, never `0.0.0.0`
- no CORS headers
- one connection per request; `sqlite3` defaults to `check_same_thread=True` and
  the server is threaded. WAL plus `BUSY_TIMEOUT` already covers concurrency.

### Content-Security-Policy

```
default-src 'self'; script-src 'self'; style-src 'self'; frame-src https://www.youtube-nocookie.com; object-src 'none'; base-uri 'none'
```

This is what makes "nothing leaves the machine" **enforceable** instead of
aspirational. Nothing on the page can phone home except the nocookie embed.

Note this forbids inline `<script>` and inline event handlers, and — less
obviously — inline `style="..."` **attributes** too, since `style-src` without
`unsafe-inline` covers those as well as `<style>` blocks. So all CSS lives in
`ui/styles.js` as one constructable stylesheet, adopted onto `document` for the
page frame and onto each shadow root by the components. That is a constraint on
how the page is written, not a detail to discover later. It is worth recording
that this works at all: constructed stylesheets are not subject to `style-src`,
because CSP has nothing to check them against — no element, no attribute, no
source URL. Verified in Chrome 154 rather than assumed, since the whole layout
would silently collapse if it were otherwise.

`object-src` and `base-uri` are additions to the four directives above.
`object-src` already falls back to `default-src` and so is not strictly needed;
`base-uri` has **no** fallback and would otherwise be unset.

Alongside it, `X-Content-Type-Options: nosniff` goes out on every response.

### The referrer policy, and error 153

The one other response header is `Referrer-Policy: origin-when-cross-origin`. It
is worth writing down at length because it was **wrong for the whole of V1.0 and
V1.1**, and because the safe-sounding choice is the one that broke the feature.

V1.0 shipped `no-referrer`. The reasoning was that a localhost URL is nobody
else's business, so the nocookie iframe should not be sending it. That reasoning
is correct and the policy still breaks the player: **YouTube refuses to configure
its embed when the request carries no `Referer`**, and reports it on the video
itself — "Video player configuration error", "Error 153", and no player. The
iframe is a real 16:9 box with a spinner that never resolves.

The cause was confirmed here rather than believed. The embed is cross-origin, so
the parent document cannot see inside it; driving Chrome over CDP and attaching to
the iframe's out-of-process target can, and reading that target's DOM returned the
error text verbatim under `no-referrer` and the video's actual title under
`origin-when-cross-origin`. `strict-origin-when-cross-origin` works too. That one
is not used, because it sends the **full URL** on same-origin requests, which
buys nothing here — this document is never framed — and leaks more the moment this
page grows a link out to somewhere. `origin-when-cross-origin` sends an origin and
nothing else: no path, no query, never the `?v=` deep link. It is the least that a
working embed accepts.

Two things keep it true rather than lucky. The value lives in `web.py` as
`REFERRER_POLICY`, next to the CSP it belongs with; and the iframe repeats it as
a `referrerpolicy` attribute, so the dependency survives someone changing the
document header, because the attribute is the narrower of the two and wins.

`cdp_check.py` reads the embed's DOM every run and fails on the string
`Error 153`. That assertion is the whole reason this section exists.

## Left pane

Three columns: channel picker furthest left, then the player, then the transcript.

The video list is **flat, newest first, across all channels**. Not grouped — see
"Why the list is not grouped by channel".

**Only videos with a transcript are rows.** Today that is 14 of the 23; the other
9 are `blocked` or `disabled` and have nothing to open. They are not hidden behind
a control or dropped in the client — the sidebar requests `status=ok`, so the
server never sends them and `meta.total` and the pager count exactly what is on
screen.

This reverses an earlier call: that a list dropping 9 of 23 is harder to trust
than one showing them. The argument assumed the dropped rows were a view of
failure. They are not — a no-transcript row is an advert for a pane that does not
exist yet, and clicking one to read "why is this empty" is failure state competing
with the thing the sidebar is for. When a dedicated failures pane arrives it owns
that question, and the endpoint's existing `status` filter is what it would query.
The sidebar never had to say "these are not videos".

The channel picker is a **native searchable combo** — an `<input list="channels">`
backed by a `<datalist>` — so the browser owns the popup, the typeahead and the
keyboard, and the page ships no code for any of it. This replaced a row of pill
buttons, which looked like a control and was not one: no typeahead, no keyboard
handling, and it grows without bound as feeds are added. Two channels today, one
more per feed.

`HAS_COMBO` feature-detects it, and the fallback is a native `<select>` — still
better than the pills. `list` has been in `HTMLInputElement.prototype` since
Chrome 20 and Safari 12.1, so this is a formality; the detection is there so an
engine without it degrades to a control rather than to a text box that filters
nothing.

The combo holds channel **names** and the filter holds channel **ids**, because
names are what a person reads and the endpoint keys on ids, so a pick resolves by
name against the published `meta.channels`. Text that is not a channel name is not
a query: rather than filtering down to nothing, the control puts back what it was
showing and changes nothing. Re-rendering is suppressed while the box has focus,
since renders happen on every load and one landing mid-word would delete what was
being typed.

There is no visible "channel" label above it. The placeholder says what the box
is for, and `aria-label="channel"` gives it the accessible name that the deleted
`<label>` used to — deleting a `<label>` without adding one leaves an unnamed text
input, which is worse to use with a screen reader than the label ever was.

Channel is the sidebar's narrowing action, not the default view: pick one and the
list refetches with `?channel=<id>`. It is a query parameter owned by
`<tessera-app>` — see "Filtering and pagination".

### What a row shows

Title, channel, and when — three things, and the three that identify a video in a
list. No reading-time estimate, no character count, no status.

**The caption `kind` is not one of them.** "auto" is a fact about the transcript,
and the sidebar has no transcript; it now lives in the transcript pane's header
next to the language, as `en  ·  auto`. That is the header's whole job when a
video has captions — it is provenance, and it belongs beside the text it
describes rather than repeated down every row.

### Dates are relative

Both places a date appears — the row and the player's caption line — say "3 days
ago" rather than `2026-09-30`. In a list spanning three months, "12 days ago"
sorts and scans better than a date you have to subtract from today yourself, and
it is the only format that stays true without the UI knowing what day it is.

`ui/format.js` owns it, because two components need it and the alternative is
two copies of a date calculation that has to agree with itself.

Three decisions worth naming:

- **Whole local calendar days, not elapsed hours.** "Today" is a local idea. A
  video published at 23:30 UTC is yesterday for most of the world and not for
  the part of it that has not gone to bed yet, so `daysAgo` compares local
  midnights. Using `Date.UTC` on the two Y/M/D triples, which is what makes that
  a comparison of whole days.
- **"1 day ago", not "yesterday".** Rows stack up against each other, and
  "1 day ago" / "2 days ago" reads as a sequence where "yesterday" / "2 days ago"
  does not.
- **The epoch guard is not fussy.** `new Date(null)` is 1970-01-01 and is a
  perfectly valid date, so a row whose `published_at` is SQL NULL — it comes from
  an RSS feed — would render "20,729 days ago" instead of nothing. `daysAgo`
  checks the type for that reason alone.

**No threshold.** A video from 2023 reads "1,128 days ago", which is the honest
consequence of expressing every date relatively, and the reason every call site
also puts the exact timestamp in the element's `title`. If that reads badly, the
fix is a threshold in one function — not a change in two components. The suite
pins the unbounded behaviour explicitly so a threshold cannot arrive unnoticed.

### Why `chars` is gone

`transcripts` stored a `chars` column for all of V1, written by the fetcher as
`len(clean_text)`. It has been dropped, along with the count it fed in the row and
in the transcript header. Three findings, in order.

**It was pure duplication.** `chars` is `length(text)` — checked against the live
corpus, where all 14 good rows match exactly and `SUM(chars)` equals
`SUM(length(text))` equals 522,508. It stored nothing that `text` did not already
say. `status_report` selected the column and read it in no branch at all; it had
been dead since V1.

**It was wrong exactly where it was being used.** The UI branched on
`chars != null` to decide "does this video have a transcript", which looks
equivalent to testing `status` and is not. A failed row stores `chars` as integer
**`0`**, not `NULL` — all nine of them, `typeof(chars) = 'integer'` — because the
fetcher writes `len(result.text or "")` and `len("")` is `0`. So every failure
rendered as "0 chars" with no status badge, and the list showed the corpus as
fourteen videos plus nine empty ones instead of fourteen plus nine problems. The
bug was caught in review; its actual cause was the column.

**A stored copy of a derivable fact is a liability, and so is a missing one.** The
obvious repair was to keep the column and make it correct — `NULL` on failure, and
`chars = COALESCE(?, chars)` so a failure could never zero a stored transcript.
That was already half of what the code did, which is the tell: `COALESCE` exists
precisely because a stored count can contradict the text it describes. The
alternative considered and rejected was `length(t.text) AS chars` in the two SELECT
lists — computed, therefore never stale, and it keeps the payload byte-identical
for free. It was rejected only because the count turned out not to be worth
displaying: a row is identified by its title, and whether it has a transcript is
already answered by the badge next to it.

So the test for "has a transcript" is `status === OK`, and there is no path by
which a stored integer can disagree with the text it was counting.

## Right pane — raw, no formatting

`text` arrives as **one unbroken single-spaced string**. Verified: zero rows out
of fourteen contain a newline, because `clean_captions` finishes with
`_SPACES.sub(" ", raw)`, which collapses every line break in the caption feed.

The client does **not** paragraph, chunk, sentence-split, or otherwise restructure
it. The string is rendered as received, inside a scrollable region. Styling still
applies — line-height, `overflow-y` — because "no formatting" means the text is not
restructured, not that it is left unstyled.

It also does not cap the measure. `.text` carried `max-width: 68ch` for the whole
of V1.1, which was a typographic opinion nobody asked for and which produced a
visible bug: the transcript stopped about two thirds of the way across its pane
while the scrollbar sat at the far edge, so the pane looked broken rather than
merely wide. `cdp_check.py` now measures the gap between the scroll container's
right border and the rightmost rendered glyph — binary-searching a `Range`'s
bounding box across the text node rather than looking for a CSS declaration —
because "is there a `max-width` in the stylesheet" is not the thing that was
wrong.

Two things this buys for free:

- A single 135KB text node renders without trouble. No chunking, no
  virtualisation, no pagination of the transcript itself.
- It is real DOM text, so browser find-in-page works. That is why no search box
  is built — the out-of-scope "search over transcripts" item stays out of scope
  for reading, and only the indexed-search question remains open.

Accepted consequence: there is no position to deep-link to, since there are no
positions. `?v=<id>` still selects a video and scrolls its row into view.

### The scroll container needs a rule of its own

`.text` is the scroll region, and it is inside `.body`, which needs
`display: flex; flex: 1; min-height: 0`. Both halves are load-bearing and neither
is obvious:

- A flex item defaults to `min-height: auto`, so **without `min-height: 0` the
  `.body` box refuses to shrink below its 134,000-character child** and the pane
  overflows instead of scrolling.
- Without `display: flex` on `.body`, the `flex: 1` and `min-height: 0` written
  on `.text` are **inert**, because they only mean anything to a flex parent.

This shipped broken and reading the CSS does not reveal it. Measured in Chrome:
the transcript host was 426px tall holding 11,527px of content with
`overflow: hidden`, `.text` reported `clientHeight === scrollHeight` so its
`overflow-y: auto` never engaged, and the document did not scroll either. Every
transcript in the corpus was truncated to its first screenful with no way to reach
the rest — including browser find-in-page, which cannot scroll to a match it
cannot scroll to.

`cdp_check.py` now asserts the geometry rather than the intent:
`scrollHeight > clientHeight` on `.text`, a bounded `clientHeight` above 100px, no
clipping on the host, `display: flex` on `.body`, and that the document itself does
not scroll.

## The `chars` migration

The column was dropped from the live corpus in place, and that is worth recording
because of *when*: YouTube was banning this IP and the RSS endpoint was 404ing, so
those 14 transcripts had no refetch path. "Run `fetch` again" was not available as
a recovery, which makes the usual "it's only a derived column" reassurance false.

What was done, in order:

1. A consistent copy via SQLite's backup API — not a file copy, since a bare
   `cp` of a WAL database can miss committed pages still in the `-wal` sidecar.
2. A sha256 over every `(video_id, lang, kind, status, attempts, error,
   fetched_at, text)` tuple, sorted, with `chars` excluded because it is the
   column being dropped. `text` is in the hash in full because it is the
   irreplaceable part.
3. `ALTER TABLE transcripts DROP COLUMN chars` — SQLite 3.35+; this is 3.53.4.
   The column was nullable, no index or view or trigger referenced it, and
   `DROP COLUMN` **refuses** rather than guessing when something does. The
   failure mode is loud, not silent.
4. The same dump. Hash identical, 23 rows, `SUM(length(text))` still 522,508.
5. `VACUUM`, because `DROP COLUMN` is a schema-only change: it frees the column
   without rewriting rows, so the space stays allocated to the file until the
   database is rebuilt. 202 pages became 150.
6. The dump again after `VACUUM`, plus `PRAGMA integrity_check`, plus the new
   `store` code reading the migrated file.

Both the hash gate and a rebuild-from-scratch version of the same migration are
asserted in `check_ui.py`, the latter against an in-memory database built with the
**old** schema — including a row written the buggy way, to prove the failure mode
cannot come back.

## Verification

Two check scripts in `/tmp`, matching the existing `check_db.py` / `check_offline.py`
convention — the repo keeps matching its own file list. 280 + 71 assertions, all
passing, plus the pre-existing ones.

`check_ui.py` is pure server-side: a real `ThreadingHTTPServer` on an OS-assigned
port, the live corpus, no writes and no network. It asserts:

- the list payload contains no `text`, no `description`, and no `chars` key at any
  depth
- `meta` does **not** publish `ok` — the client hardcodes it, and publishing it is
  the bug this reversed
- `meta` carries **exactly** `{total, limit, offset, has_more, channels}`, asserted
  as a set so a key nobody reads fails in both directions, and every one of those
  five is separately asserted to be genuinely read somewhere in the client. The
  reverse direction is not checkable the obvious way — `video-list.js` has a DOM

- every file under `ui/` appears in the static allowlist, and every `import`
  specifier in the client resolves to a file that is both on disk and allowlisted —
  the forward direction alone would let a renamed component 404 at runtime with no
  error anywhere

  stripped first, since both names survive in the comments explaining their removal

  the **old** schema, including a row written the buggy way: text untouched,

- row count and per-status counts agree with `tessera status`
- `/api/videos/<id>` 404s cleanly on an unknown id, and 400s on a malformed one
  (`^[A-Za-z0-9_-]{11}$` is validated before any query is built)
- a row with no transcript is still a 200 carrying its stored reason, not a 404
- the read-only opener refuses a write, while the normal opener is not read-only
- the CSP header is present and lists only the nocookie frame origin; `POST` is
  405 with `Allow: GET, HEAD`; a traversal attempt is 404
- paging partitions the corpus exactly: concatenating every page's `rows` at
  limits 1, 2, 3 and 7 yields the same video_ids as one unpaged call, with no gap
  and no duplicate at a page boundary. This needs a unique tiebreaker in
  `ORDER BY` — `video_id` is carried as a secondary sort precisely so equal
  `published_at` values cannot reorder across pages
- `meta.total` shrinks when `channel` is given, and equals the unpaged count when
  it is not
- `meta.has_more` is true on a short page only when more rows remain
- `limit=99999` clamps to 500 rather than returning everything
- `limit=abc`, `limit=-1`, `offset=abc`, `offset=-1`, `offset=1.5` each 400
  rather than silently defaulting; `limit=` (blank) is the default
- `?channel=<unknown-id>` returns `rows: []` with `total: 0`, not a 500 — and so
  does an unknown `status`, by the same reasoning
- changing a filter while `offset > 0` resets the request to `offset=0`
- `tessera ui` opens `http://127.0.0.1:8787` exactly once, exits 1 without
  opening a browser when the port is taken, and an unknown command exits 2
- every path in the static allowlist exists on disk inside the package

`cdp_check.py` is the part nothing else could cover: it drives real Chrome over
the DevTools protocol with a stdlib-only websocket client, because the assertions
below are about the browser and cannot be settled by reading code. It asserts:

- all four custom elements are defined and upgraded with a shadow root
- the constructable stylesheet reaches the document **under `style-src 'self'`** —
  asserted as 40 parsed rules and a resolved `--bg`, and the palette stays light

- the header carries no `read-only` tag and the title reads `Tessera`
- the channel picker is an `<input list="channels">` whose datalist id matches its

- **the page load makes exactly one `/api/videos` request, and it carries

- typing a channel name and firing `change` reaches `<tessera-app>`, narrows the

  reverted and does **not** filter the list to nothing
- clicking a row reaches `<tessera-app>`, moves `aria-current`, rewrites `?v=`,
  moves the embed, and loads the transcript
- the transcript header names the language **and the caption kind** as `en  ·  auto`
  — the same `kind` that is no longer on the row, asserted in its new home so the
  move is pinned at both ends
- the corpus's one `disabled` video is **not a row** and cannot be clicked, but
  navigating straight to `?v=WPjbpoKWYN4` still shows its stored status and reason
  in the right pane rather than an empty one — the old way in is gone, but the
  pane that answers "why is this empty" is still reachable

Five real bugs came out of this and are fixed:

1. A null-`meta` dereference in the pager that threw on the very first render.
2. A client that set the `status` filter without re-requesting, so the list
   displayed all 23 rows while claiming `?status=ok`. Bugs 1 and 2 were the same
   mistake wearing different hats, and both are the reason the default filter is
   now a literal rather than a negotiation.
3. The `chars`-vs-`status` row test — see "Why `chars` is gone".
4. **The transcript pane did not scroll.** Every transcript was clipped to its

5. **The provenance header was written to the wrong element.** `#render()` set

   header was unhidden and left empty while the line landed as the first line
   *inside* the scroll container. Cosmetic, and invisible to every assertion here
   — a layout bug that only shows up when you read the rendered text back out of
   the browser.

Bug 5 is the one worth remembering. It survived a 244-assertion suite and a
48-assertion browser suite, because both were asserting that the pane *had* a
header rather than that the header had anything in it. Reading the rendered text
is not the same as reading the code that produces it.

## Grounded ASR entity normalization

Motivated by the first summarization run, where the two local models disagreed on
every Spanish name in `d61n1isTfeo`. The transcript is auto-captions and already
wrong: the title says *The Hunt for El Mencho*, while the transcript never writes
"El Mencho" at all — it writes "El Meno" once and fused or truncated spellings
("Elmeno" ×15, "Elmen" ×4, "Elmenure", "Elmenro") the rest of the time. (The
"17 times" this section first claimed was the substring `meno`, mostly Spanish
`menos`.) `clean_captions` is faithful to that — it only
strips noise — so the error is YouTube's and the summarizer inherits it.

Faced with the noise, the two models split:

- `e4b` copies the transcript's surface form ("El Meno", "Kaliscoco", "Mituakan");
- `12b` repairs from its own parametric memory when it recognises the entity
  ("El Mencho", "Tapalpa") and copies the rest verbatim, including a name that
  does not exist ("Nessia Rubin Oera Cantes").

That is a knowledge difference, not a reading difference, and it is
unverifiable: nothing in a `12b` output distinguishes a correct repair from a
hallucination. It also contradicts the prompt's own rule — *use only the provided
data, do not add facts from your general knowledge*.

Two grounded fixes follow, in increasing ambition. Both keep the
no-external-knowledge rule intact, and neither writes the database. A third
option — a free-running LLM cleanup pass — is deliberately **out of scope**: it
trades known errors for invisible ones, and there is no verifier to tell the two
apart.

### Recommendation 1 — deterministic glossary correction from metadata

The claim: the video's own `title`, `description`, and `channel_name` are data we
already hold, and the entity that matters most is usually in them. For
`d61n1isTfeo` the title carries `El Mencho` and the description carries `El
Mencho` and `CJNG`. A pure string pass recovers those with no model and no guess.

Design:

- New pure module (`tessera/normalize.py`, or `tools/normalize.py` if it stays an
  experiment): `normalize(text, metadata) -> (clean_text, edits)`.
- Build a glossary from `title + description + channel_name`. Candidates are
  capitalised words and multiword runs, all-caps acronyms of two or more letters,
  and names in quotes or parentheses. Drop URLs, emails, and the sponsor/music
  boilerplate that dominates those descriptions.
- Match transcript tokens, and 1–3 word windows, against the glossary under two
  cheap keys: casefolded/accent-stripped equality, and a phonetic key
  (Soundex/Metaphone-style) with a bounded edit distance as a tie-break.
- Replace only on a confident, unique best match. If two candidates tie, or the
  best score is below threshold, the text is left alone.
- Every edit is recorded (`from`, `to`, `method`, `score`, `count`) and returned;
  cap the number of edits per transcript.
- `transcripts.text` is never touched. The normalised text is derived, cached
  beside the summaries, and diffable.

Why deterministic: it cannot invent a name, and a bad replacement is always
traceable to a metadata string a human can check. It is also idempotent and
unit-testable.

Expected effect: `El Mencho` and `CJNG` are fixed. `Tapalpa`, `Michoacán` and
`Veracruz` are not in this video's metadata and stay wrong — an accepted limit,
not a bug.

### Recommendation 2 — metadata in the prompt, plus a grounded spelling rule

Two changes, one of which is not code at all.

- **Feed the metadata.** `tools/summarize.py` already selects `title`,
  `channel_name`, `url` and the transcript text, but not `description`, and
  `call_model` sends only the prompt and the transcript: the models never see the
  title today. Add `description` to the query and a `METADATA` block (title,
  channel, description) ahead of `TRANSCRIPT`.
- **Add a rule to `prompt`** (the user's file, so it needs their sign-off).
  Shape:

  > PROPER NOUNS. The title and description are provided as METADATA. If a name
  > in the transcript matches a name in METADATA, use the METADATA spelling.
  > Never correct a name from outside METADATA or the transcript. If a name is
  > unclear, keep the transcript's spelling rather than guessing.

- **Quotes stay verbatim.** The prompt demands an "exact, short, searchable
  excerpt". The only thing that is searchable is the stored `transcripts.text`,
  so a quote is copied from the *original*, not the normalised text. The narrative
  may use the metadata spelling; the quote does not.

The two fixes compose. With (1) alone the metadata spelling is already in the
text; with (2) alone the model has the spelling to hand. Running both means (2)
is the guard for whatever (1) did not catch, and the explicit clause removes the
licence the `12b` took to correct names on its own.

### Files

- `prompt` — new PROPER NOUNS rule (user-owned).
- `tools/summarize.py` — select `description`; send the `METADATA` block; run the
  normaliser when enabled; render the edit list on the page.
- new `tessera/normalize.py` (or `tools/normalize.py`) — the pure pass.
- `plan.md` — this section.

### Verification

- Unit tests on the normaliser, driven through the real function: accent and case
  fold; one-character substitution; multiword ("El Meno" → "El Mencho");
  ambiguity (two candidates tie → no change); empty metadata → identity; and
  idempotence (a second pass yields zero edits).
- A golden case from `d61n1isTfeo`: the edit list contains `El Meno → El Mencho`
  (all 17 occurrences) and leaves `CJNG` alone. `Kaliscoco` is **not** touched —
  pinned as an expected miss, so a future over-eager matcher fails loudly.
- The database is untouched: hash `transcripts.text` before and after a run.
- Both models re-run over the normalised text; assert `El Meno` no longer appears
  in either output, and that no proper noun appears which is absent from both the
  transcript and the metadata — the fairness check that makes the e4b/12b
  comparison about summarisation again.
- The `METADATA` block is asserted to reach the request payload, not merely the
  database row.

### Accepted limits

- Only entities present in the metadata can be corrected; the long tail
  (`Tapalpa`, `Michoacán`, `Veracruz`) stays noisy by design.
- Descriptions polluted with sponsor and music boilerplate are the hard case for
  the glossary extractor; it has to filter that noise, at the risk of dropping a
  real name.
- Some channels keep descriptions to a couple of hundred characters, so for those
  videos both passes will do almost nothing — acceptable, since they carry few
  non-English names.

### Open questions

- Does the normaliser belong in `tessera/` (shipped, tested) or stay in `tools/`
  beside the experiment?
- Should quotes be rewritten to the metadata spelling for reader convenience,
  at the cost of no longer matching `transcripts.text` under a copy-paste search?
- If YouTube ever serves a manual track, `kind=manual` is the cheaper fix: trust
  it and skip both passes.

### Implementation notes

Implemented 2026-10-03, recommendations 1 and 2 only.

- **Where it lives.** `tools/normalize.py`, beside the experiment, so the shipped
  `tessera` package and its UI tests stay untouched. CLI:
  `uv run python tools/normalize.py <video_id>` prints the glossary and the diff.
- **Matching changed from the sketch.** The first draft used SequenceMatcher (a
  gestalt ratio) and a phonetic key; it was far too eager — it rewrote
  `cartels`→`Cartel`, `Mexico`→`Mexico's`, `CJNG`→`CJNG A`, `American`→`Mexican`,
  `Nacho`→`Mencho`. The shipped matcher is narrower:
  - the glossary holds all-caps acronyms and multiword name runs only, with
    single words taken from the title alone (not the description), and connective
    words trimmed off run edges;
  - a window may not be longer than its name, must be name-like, and when the word
    counts agree every leading word must match exactly and the last word is
    compared only against a very close single-word threshold (`0.85`) or a looser
    multiword threshold (`0.70`);
  - a fused token (`Elmeno` for `El Mencho`) matches on common prefix (`0.60`);
  - a word differing only by case, accents, plural or possessive is left alone;
  - acronyms are never fuzzy-matched.
  This catches the intended errors across the corpus (`El Meno`/`Elmeno`/`Elmen`/
  `Elmenure`/`Elmenro`→`El Mencho`; `Maya Kauffman`→`Maya Kaufman`; `Carmen
  Laauo`→`Carmen Lau`; `Joe Piston`/`Pisone`/`Pone`→`Joe Pistone`; `Donnie
  Bras`/`Verasco`→`Donnie Brasco`) and leaves clean transcripts untouched.
- **Recommendation 2's rule lives in `prompt`** (the user's call): a "Proper
  nouns" bullet in the RULES list, and `tools/summarize.py` composes
  `prompt + METADATA`. During implementation the rule was briefly injected from
  code, to avoid splitting the live comparison run by editing `prompt` mid-run;
  it moved into the file once that run was stopped.
- **Defaults and flags.** Normalization and metadata are on by default;
  `--no-normalize` and `--no-metadata` restore the old behaviour per run. Cached
  base runs predate the feature and carry no `normalize` provenance, so their
  pages show no grounding note.
- **Quote caveat.** Because the model is fed the normalized transcript, a quote
  reflects the metadata spelling; it will not match `transcripts.text` for a
  corrected name. Feeding the original for quoting and the metadata for spelling
  remains open (see Open questions).
- **Tests.** `tests/test_normalize.py` (plain script, no pytest) — 15/15:
  identity with no metadata, case/accent-only, plural, possessive, lowercase,
  multiword, fused, leading-word mismatch, term-extension, acronym, ambiguity,
  idempotence, two clean-corpus checks, the `d61n1isTfeo` golden case, and a
  DB-unchanged check.
  Golden: exactly one `El Meno → El Mencho`, 22 name repairs total, `CJNG` and
  `Kaliscoco` untouched, second pass zero edits.

# Tessera — V2: fetch → normalize → summarize

V1 stored transcripts and V1.1 showed them. The grounding experiment (above) gave a
deterministic normaliser and a `prompt` that names the metadata as the only
spelling authority. V2 connects the two programs: **one command, `fetch`, now
normalises each transcript and then summarises it, and the summary is stored in the
database beside the raw transcript.** The browser UI shows the summary first, with
the full transcript behind a disclosure underneath it.

The benchmark is finished and is not run again. The recommendation from the last
benchmark pass is the production configuration: `gemma4:e4b-mlx` with thinking
off — fastest, lightest, every run complete, and its one real weakness (copying
ASR spellings) is exactly what the metadata grounding now fixes. `12b` was ~3×
slower and misspelled the section-4 heading in every run; thinking made naming
worse and, for `12b`, silently returned empty answers after spending the whole
output budget. None of that is carried into production.

## Decisions

1. **Model.** `gemma4:e4b-mlx`, thinking off, `temperature 0`, `seed 42`. One call
   per transcript, whole transcript, no chunking.
2. **Inline, per video.** Normalise and summarise immediately after each
   transcript is stored, inside the fetch loop, not as a second pass. The LLM call
   is slow (tens of seconds), which *adds* spacing between two YouTube requests on
   top of `POLITE_DELAY` — the delay the ban-avoidance work asked for, for free.
3. **Ollama is optional at runtime.** If the model call fails, the transcript is
   already stored and stays stored; the summary is recorded as `error` and a later
   `fetch` retries it. A transport failure is treated as *not an attempt*, the same
   way a `blocked` transcript is not an attempt — an Ollama that is not running
   says nothing about the video.
4. **A dedicated `summaries` table**, one row per video, not columns bolted onto
   `transcripts`. `transcripts` is about fetching; `summaries` is about the model.
5. **KISS on prompt changes.** No prompt hash, no regeneration, no versioning. An
   edit to `prompt` applies to summaries generated *after* it; existing rows are
   left alone. (User's call, and it keeps the schema small.)
6. **The normalised text is stored and is what the UI shows.** The normalised copy
   is the better-quality text, so it is the "full transcript" in the disclosure,
   not the raw `transcripts.text`. This also makes the prompt's quote rule honest:
   a quote from the normalised text is searchable in the normalised text the reader
   is looking at.
7. **The summary is rendered safely**, never as raw HTML: model output is parsed
   into headings, lists and `<strong>` via text nodes only.

## Pipeline

`cmd_fetch` keeps its two transcript sources and gains a third, summary-only one:

| source | fetch? | then |
|---|---|---|
| new feed entries | yes | normalise + summarise |
| retryable transcripts (`blocked`/`error`/`pending`, `attempts < MAX`) | yes | normalise + summarise on `ok` |
| `ok` transcripts without a valid summary | no | normalise + summarise |

The third row is both the initial backfill for the existing corpus and the repair
path after an Ollama outage. Selection:

```sql
SELECT v.video_id
FROM transcripts t
JOIN videos v ON v.video_id = t.video_id
LEFT JOIN summaries s ON s.video_id = t.video_id
WHERE t.status = 'ok' AND t.text IS NOT NULL AND t.text <> ''
  AND (s.video_id IS NULL OR (s.status <> 'ok' AND s.attempts < :max_attempts))
```

Transcript work runs first, spaced by `POLITE_DELAY` *and* the model call; the
summary-only backlog runs after, with no YouTube request in it. A `blocked`
transcript still stops the transcript loop as it does today; the backlog that
follows has nothing to fetch, so it can still run.

For each `ok` transcript the sequence is:

1. load the video's own metadata (`title`, `channel_name`, `description`);
2. `normalize(text, metadata)` → `(normalized_text, edits)`; the stored
   `transcripts.text` is never touched;
3. compose `prompt` + `METADATA` block, send `normalized_text`;
4. store the result.

## Schema

```sql
CREATE TABLE IF NOT EXISTS summaries (
  video_id        TEXT PRIMARY KEY REFERENCES videos(video_id),
  status          TEXT NOT NULL,      -- ok | error
  text            TEXT,               -- model output, verbatim; NULL on error
  normalized_text TEXT,               -- the input the model saw, and what the UI shows
  model           TEXT,               -- e.g. gemma4:e4b-mlx; provenance only
  attempts        INTEGER DEFAULT 0,
  error           TEXT,
  generated_at    TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_summaries_status ON summaries(status, attempts);
```

`normalized_text` is written even when the model call fails, so a grounded
transcript is still available to the UI while the summary is retried. No timing or
token columns: the benchmark needed them, production does not.

`store.record_summary` upserts one row; on an `error` that is a *transport* failure
it leaves `attempts` alone, mirroring `store.record`'s treatment of `blocked`. A
summary row with `status = 'ok'` is never re-selected, which is decision 5 in code.

## The model call

`tessera/summarize.py` is the production cut of `tools/summarize.py`: the Ollama
call, the `METADATA` block, and the dynamic context sizing, with the benchmark
apparatus (variants, `think`, `pilot`/`run`/`render`, HTML, the `summaries/`
cache) gone.

- `POST {OLLAMA_URL}` with `stream: false`, `keep_alive`, `temperature 0`,
  `seed 42`, `num_predict 2048`, and `num_ctx` sized from the transcript exactly as
  the experiment did (floor 32768, step 8192, ceiling 131072).
- Returns a small result object: `status`, `text`, `normalized_text`, `error`,
  and whether the failure was transport-level.
- The `prompt` file stays user-owned and is read from `config.PROMPT_PATH`; the
  section 7 removal is already in the file and the code makes no assumption about
  how many sections there are.

`tessera/config.py` gains `PROMPT_PATH`, `OLLAMA_URL`, `SUMMARY_MODEL`,
`SUMMARY_TEMPERATURE`, `SUMMARY_SEED`, `SUMMARY_NUM_PREDICT`, `SUMMARY_KEEP_ALIVE`,
`SUMMARY_TIMEOUT`, the context constants, and `SUMMARY_MAX_ATTEMPTS`.

## UI

The right pane becomes **summary first, transcript behind a disclosure**, and keeps
the existing `<tessera-transcript>` element (no new static route).

- Header: the caption provenance (`lang · kind`) as today, plus the summary state.
- Summary body: the model output parsed into section headings, paragraphs and
  bullet lists, bold rendered as `<strong>`. All text goes through `textContent`;
  nothing from the model is ever interpolated as HTML or CSS, so neither the CSP
  nor the "nothing leaves the machine" rule is weakened.
- Below it, `<details><summary>Transcript</summary>…`: closed by default, and the
  disclosure's body is the stored `normalized_text` (falling back to `text` when a
  summary row has no normalised copy). The summary area keeps its own scroll; the
  expanded transcript scrolls inside the remaining height.
- When the summary is missing or `error`, the pane shows that state — with the
  stored reason — and still offers the transcript disclosure.

`store.get_video` gains a `LEFT JOIN summaries` and the summary columns; the list
payload is unchanged. `web.py`'s routing is unchanged. `cmd_ui` runs `store.init`
once before serving so an older `tessera.db` grows the `summaries` table before a
read-only connection ever sees it; the serving path stays `mode=ro`.

## Accepted limits

- **The `Elmano` gap survives.** The normaliser fixes `Elmeno`/`El Meno` but not
  `Elmano` (15 occurrences in `d61n1isTfeo`): it shares only a 3-character prefix

- If Ollama is never available, every video carries an `error` summary and is
